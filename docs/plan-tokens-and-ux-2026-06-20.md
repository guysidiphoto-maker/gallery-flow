# תוכנית עבודה — אתר Pixflow: טוקנים (תשלום) + שיפור UX/UI

**נכתב:** 20.6.2026
**הקשר:** מתמקדים ב**אתר** (`gallery-web/`), לא באפליקציית הדסקטופ.
מטרת-העל של האתר: שצלמים ישתמשו בו כ**ענן + תוכנת זיהוי פנים** — ויוכלו לשלם עליו.

> **מונחי יסוד:**
> - **טוקן (token)** = "מטבע" פנימי. כל תמונה שמועלית מנכה טוקן אחד.
> - **edge function** = פונקציית שרת קטנה שרצה אצל Supabase (ספק מסד-הנתונים שלנו).
> - **webhook** = כתובת אצלנו שספק התשלום "דופק" עליה אוטומטית אחרי שמישהו משלם, כדי שנדע לזכות טוקנים.
> - **env var** (משתנה סביבה) = הגדרה סודית (מפתח/מזהה) ששומרים מחוץ לקוד.
> - **RPC** = פעולה במסד הנתונים שהקוד קורא לה בשם.
> - **LemonSqueezy** = ספק התשלום שנבחר. יתרון: הוא ה-Merchant of Record — מטפל בעצמו במע"מ/חשבוניות מול הלקוח, פחות כאב ראש רגולטורי.
> - **design tokens / design system** = סט אחיד אחד של צבעים, גופנים, מרווחים ורכיבים, שכל המסכים משתמשים בו.

## חלק א' — טוקנים: לגרום לקנייה לעבוד מקצה-לקצה (LemonSqueezy)

### מצב נוכחי (אומת בקוד)
- ✅ **ה-UI לקנייה** קיים (`tokenClient.ts` + מודל "קנה טוקנים" ב-`Dashboard.tsx`/`StudioSettings.tsx`).
- ✅ **צריכת טוקנים** עובדת ואטומית — `record_image_upload` מנכה טוקן + מכניס תמונה בעסקה אחת.
- ✅ **ה-webhook של LemonSqueezy** (`supabase/functions/lemonsqueezy-webhook/index.ts`) בנוי במלואו: מאמת חתימה, ממפה variant→plan, מזכה טוקנים דרך `add_tokens`, אידמפוטנטי (webhook חוזר לא מזכה פעמיים), מנהל גם ביטול/חידוש מנוי.
- ❌ **החיבור שבור:** `tokenClient.startCheckout` קורא ל-edge function `create-checkout` ומצפה לשדה `checkoutUrl`, אבל `create-checkout` כתוב ל-**Stripe** (ספק אחר), מחזיר שדה בשם `url`, ודורש env vars של Stripe שריקים. לכן לחיצה על "קנה" נכשלת מיד.

### השלבים

**שלב 0 — הקמת חשבון LemonSqueezy (משימה שלך, לא קוד)**
מה אתה צריך לעשות בלוח הבקרה של LemonSqueezy (אני אדריך צעד-צעד):
1. ליצור Store (חנות).
2. ליצור 2 מוצרים/variants: **Pro** (2,000 טוקנים, ~79₪/חודש) ו-**Business** (10,000 טוקנים, ~159₪/חודש).
3. להעתיק את ה-**variant IDs** האמיתיים (הקוד היום מניח `1519997`/`1520026` — צריך לעדכן למזהים האמיתיים).
4. להעתיק: `LEMONSQUEEZY_API_KEY`, `LEMONSQUEEZY_STORE_ID`, ו-`LEMONSQUEEZY_WEBHOOK_SECRET`.

**שלב 1 — להחליף את `create-checkout` ל-LemonSqueezy (קוד)**
- לשכתב את `supabase/functions/create-checkout/index.ts` כך שייצור checkout של LemonSqueezy (דרך ה-API שלהם) במקום Stripe.
- **קריטי:** להטמיע ב-checkout את `custom_data.business_id` — כי ה-webhook קורא בדיוק את `event.meta.custom_data.business_id` כדי לדעת למי לזכות טוקנים. בלי זה הזיכוי לא יקרה.
- להחזיר `{ checkoutUrl }` (השם שה-`tokenClient` מצפה לו), לא `url`.

**שלב 2 — לעדכן את המיפוי והסודות (קוד + הגדרה)**
- לעדכן `VARIANT_TO_PLAN` ב-webhook עם ה-variant IDs האמיתיים משלב 0.
- להגדיר את כל ה-env vars (api key, store id, webhook secret) על Supabase.
- לרשום את כתובת ה-webhook שלנו בלוח הבקרה של LemonSqueezy ולבחור את האירועים (`subscription_created`, `subscription_payment_success`, `order_created`, `subscription_cancelled`, `subscription_expired`).

**שלב 3 — ניהול מנוי בסיסי (UX קצר)**
- להוסיף בדשבורד קישור "ניהול מנוי / חיוב" (LemonSqueezy מספק Customer Portal מובנה) — כדי שצלם יוכל לבטל/לעדכן אמצעי תשלום לבד, בלי לפנות לתמיכה.
- להציג בבירור את התוכנית הנוכחית והיתרה.

**שלב 4 — בדיקה מקצה-לקצה (Test Mode)**
- במצב בדיקה של LemonSqueezy: ללחוץ "קנה" → להגיע ל-checkout → לשלם בכרטיס בדיקה → לוודא שה-webhook זוכה טוקנים ושהיתרה עלתה. גם לבדוק ביטול-מנוי → ירידה ל-starter.

### החלטה מוצרית פתוחה (דורשת אותך)
**האם זיהוי פנים צריך לצרוך טוקנים?** היום רק העלאת תמונות צורכת; זיהוי פנים (שעולה לך כסף ב-AWS) חינמי. שתי אפשרויות:
- **להשאיר כמו שזה** — פשוט, אבל העלות שלך לא חסומה.
- **לחייב טוקנים על זיהוי פנים** (למשל טוקן לכל X תמונות שמאונדקסות, או לכל חיפוש) — מחבר את העלות שלך להכנסה.
*המלצה:* בשלב ראשון להשאיר כמו שזה ולהשיק תשלום; לחזור לזה אחרי שיש נתוני שימוש אמיתיים.

## חלק ב' — UX/UI: מ"שלושה מוצרים שונים" למוצר אחד מלוטש

### מצב נוכחי (אומת בקוד)
הבעיה אינה מסך בודד — אלא ש**אין מערכת עיצוב אחת**:
- **שלוש שפות עיצוב נפרדות:** דף נחיתה (כהה־סגול), צפיית גלריה (כהה־פחם), דשבורד (קרם־פחם). המעבר ביניהן מרגיש כמו שלושה מוצרים.
- **אין Tailwind, אין ספריית רכיבים, אין קובץ צבעים מרכזי.** העיצוב כתוב inline (ישירות בתוך הקוד) באלפי מקומות; הצבעים מוגדרים מחדש ב-4 קבצים שונים.
- **`Dashboard.tsx` הוא קובץ ענק (~6,900 שורות)** עם עיצוב inline בכל פקד.
- **אין דף תמחור אמיתי**; התמחור קבור בתוך דף הנחיתה.
- כבר קיימים ב-git ענפי-עיצוב ישנים (`web/light-theme-redesign`, `design/editorial-polish-pass` וכו') — נאחד מתוכם את הטוב, לא נתחיל מאפס.

### העיקרון
**קודם זהות עיצובית אחת, אחר כך מחילים אותה על הכול.** שיפור מסך-מסך בלי בסיס משותף רק יגדיל את הבלגן.

### השלבים

**שלב 0 — החלטת זהות (משימה שלך + הצגה שלי)**
- לבחור כיוון ויזואלי אחד (כהה אלגנטי / בהיר נקי / "אדיטוריאלי"). אציג 2-3 כיווני צבע+טיפוגרפיה להשוואה.
- אם יש לך עיצובים ב-Figma — אפשר למשוך מהם ישירות (יש לנו חיבור ל-Figma).
- *(זיכרון קודם שלך: דפי הנחיתה נראים "AI-generated" וצריך זהות עיצובית אמיתית — זה בדיוק מה שהשלב הזה פותר.)*

**שלב 1 — בסיס עיצוב משותף (קוד, סיכון נמוך)**
- ליצור `gallery-web/src/theme.ts` — מקור-אמת יחיד: פלטת צבעים (4-5 צבעים), סולם גופנים (כותרות/גוף/תווית), סולם מרווחים, רדיוסים, צללים.
- ליצור 4-5 רכיבי-בסיס משותפים: `Button`, `Card`, `Modal`, `Input`, `Badge` — עם נגישות מובנית (focus ring, מקלדת) ותמיכת RTL נכונה.
- בלי לשבור מסכים קיימים — מוסיפים את הבסיס לצד הקיים.

**שלב 2 — להחיל על המסכים, אחד-אחד (כל מסך = PR נפרד)**
סדר מומלץ לפי השפעה:
1. **דף נחיתה + דף תמחור** — הרושם הראשון; כאן צלם מחליט אם להירשם. כולל יצירת route ייעודי `/pricing` וניסוח מסר ברור ("אורחים מוצאים את התמונות שלהם תוך שניות עם זיהוי פנים").
2. **דשבורד הצלם** — להחיל את ה-theme + לפרק את המפלצת ל-15-20 רכיבים ממוקדים (שיפור מהירות + תחזוקה).
3. **צפיית הגלריה** (אזור הלקוח-קצה) — להאחיד לאותה זהות.
4. **דשבורד/פורטל הלקוח** — האחדה אחרונה.

**שלב 3 — ליטוש רוחבי**
- טיפוגרפיה אחידה (סולם אחד, לא 11 גדלים אקראיים).
- RTL עקבי בכל המסכים (היום שבור בדף הנחיתה).
- ניקוי גופנים מיותרים (נטענים 7, בשימוש 3).

## עקרונות עבודה (סטנדרט קבוע)
- כל שלב = PR ממוקד אחד; עוצרים ומדווחים בין שלבים.
- לא לשבור את הגלריה הציבורית או את אימות הלקוח.
- אין SQL הרסני בלי תצוגה-מקדימה; אין פריסה אוטומטית — אתה מאשר.
- main מוגן (מיזוג רק דרך PR); אחרי כל שינוי קוד אציע commit + push.
- אימות אמיתי ב-preview/פרודקשן, לא רק על סמך build logs.

## סדר ביצוע מוצע (כשתאשר)
1. **טוקנים שלב 0** (הקמת LemonSqueezy — אני מדריך אותך) — חוסם הכנסות, הכי דחוף.
2. **טוקנים שלבים 1-2** (קוד החיבור) — במקביל לשלב 0.
3. **UX שלב 0-1** (זהות + בסיס עיצוב) — אפשר במקביל לטוקנים, כי לא נוגע באותם קבצים.
4. ואז שלב-אחר-שלב לפי הטבלאות למעלה.
